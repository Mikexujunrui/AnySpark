## 一、为什么需要这份规划

- **候选评估结论（主人质询驱动）**：收编内存 batch 值得做，但"直接删 = 自断后路"——
  workflow 的杀手级优势（长任务可靠性）未兑现：引擎层断点恢复已有（S129），但
  **无 resume 续跑入口**（重启后任务状态在 DB 却无法续跑）；**无版本回溯能力**
  （chapter_versions 表有快照数据，但无恢复端点、无批级标识，用户不可达）。
- **回溯能力现状**：每次 upsert 覆盖前自动存旧版（`note='修改前'`），数据层已就位；
  缺 ① 恢复入口（端点+UI）② 批级标识（note 固定，无法定位"哪次批量任务改的"）。
- **规模化修改必须先有安全网**：300 章跑 5-8 小时，中断不能续 = 白跑；跑完不满意
  不能回滚 = 灾难。安全网是收编的前置条件，不是并列项。

## 二、依赖链（安全网在前，减法在后）

```
A 续跑安全网 ─┐
             ├─→ C 中规模实测（A+B 闭环验证）─→ D 收编内存 batch + 前端收尾
B 回溯安全网 ─┘
```

## 三、阶段分解

### 阶段 A：续跑安全网（~30-60 分钟）
- **resume 入口**：`POST /api/workflows/tasks/{id}/resume` —— 对 running/failed/
  waiting_approval 任务再跑 `run_task`（引擎幂等续跑已有，只补应用层入口）。
- **验证**：测试 + 手动实测（跑任务 → 模拟中断 → resume 续跑，迭代数不重跑）。

### 阶段 B：回溯安全网（~1.5-2 小时核心 + 前端 UI ~1 小时）
| 子项 | 内容 | 说明 |
|---|---|---|
| B1 | upsert note 携带来源 | note 从固定 `'修改前'` 改为可传来源（`'批量改写'` + workflow task_id），`write_chapter` script 传任务标识——批级定位的基石 |
| B2 | 单章恢复端点 + 前端版本历史 UI | `POST /api/chapters/{id}/restore`（当前内容先入版本、目标版本写回）+ 前端查看/恢复按钮 |
| B3 | 批级一键回滚 | `POST /api/workflows/tasks/{id}/rollback` —— 任务记录涉及章节改前快照（按 B1 来源/任务标识聚合），一次回滚该任务所有改动 |

- **验证**：恢复测试 + 回滚测试（改 N 章 → 一键回滚 → 全部还原）。

### 阶段 C：中规模实测（~1 小时）
- 用「章节加料」/「批量改写」模板对**真实库跑 10-20 章**（S137 已备好载体，非敏感指令）：
  - 大 loop 引擎稳定性（迭代上限/内存/进度）
  - 中断 → resume 续跑真实可用
  - 不满意 → rollback 一键回滚闭环
- **验证标准**：三件事全绿，才算"规模化可信赖"成立。

### 阶段 D：收编内存 batch + 前端收尾（~1-1.5 小时）
- **前提：A+B+C 全绿**（删才是无风险减法——替代品已验证可靠 + 有续跑和回滚能力）。
- 后端：删 `routes_agency.py` 的 `/api/batch/*` 路由 + `deps` 的 batches/batch_queue/
  batch_lock + `tasks.py` 的 run_batch_rewrite/review（底层 chapter 读取等函数保留）。
- 前端：BatchPanel 删旧模式，只留工作流模式（S133 已并存）。
- 测试改造 + 全量 gate。
