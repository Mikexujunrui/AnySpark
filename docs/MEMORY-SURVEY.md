# 心智模型 vs 主流跨会话记忆系统——对比沉淀与接线决策

> 日期：2026-08-14 · 决策人：主人 + pi 会话 · 对应实施：S132 / S132b / S132c（DESIGN §12.45）
> 目的：留作后续记忆系统选型/再评估的参考，避免重复论证。

---

## 1. 背景

主人要求客观对比 V4 心智模型与主流跨会话记忆系统（以 oh-my-pi 的 Hindsight 记忆系统为代表），
并基于"V4 是做加法的加法、但必须保持克制"的原则，判断是否有值得学习的地方。

## 2. 对比对象澄清

- **V4 心智模型**（`manual` 表 + `MindPlanner`）：管"怎么写/怎么协作"——偏好/习惯/雷区/协作约定。
  输出是一个**策略决策**（SessionPlan），指导主循环规划会话。事实记忆另由图谱/项目档案承担。
- **OMP + Hindsight**：管"发生过什么"——会话 transcript 的事实提取 + 向量召回。
  其 mental models（user-preferences/project-conventions/project-decisions）是最接近"心智"的部分，
  但本质是服务端自动维护的总结缓存，不可编辑。

严格说，V4 心智的对手不是整个 Hindsight，而是其 mental-models 层；Hindsight 整体
（含向量事实召回）对标的应是 V4 心智+图谱的合体。

## 3. 核心差异（修正后的客观版）

| 维度 | V4 心智模型 | OMP + Hindsight |
|---|---|---|
| 存储 | 自然语言短句 + 元数据（来源/置信度/活跃度/锁定），SQLite，明确不用向量 | 向量 embedding + 服务端事实提取 |
| 检索 | FTS5 + 双字关键词重叠 + LLM 语义挑选 | 向量语义召回（对同义改写鲁棒） |
| 披露 | 渐进式披露（锁定→活跃度→context→置信度，前 5 条） | mental models 全量拼入每次 prompt + 召回带 preamble 过滤 |
| 用户可读可改 | ✅ 全 CRUD + 锁定；用户主权是设计原则 | ❌ hindsight 后端无 memory_edit（mnemopi 本地后端有）；只能 UI 删 bank |
| 写入 | 7 种方式（登记/提炼/手动/负例/对账/弱信号/展示） | 全自动：防抖 retain 队列 + 每 N 轮 transcript 提取 |
| 纠正 | mind_update/mind_delete + manual_notices 变更通知 | 无用户侧纠正通道（靠 reflect 综合） |
| 作用域 | global / project 两层 | global / per-project / per-project-tagged 三态 |
| 生命周期 | 会话开披露 + 归档提炼（S132 前靠手动触发） | 首轮 auto-recall + 每 N 轮 auto-retain，零配置 |
| 模型耦合 | 模型无关（换模型不丢，硬原则） | 向量绑定 embedding 模型，换模型需重嵌 |
| 依赖 | 纯本地 SQLite | Hindsight 服务器（云/自托管）或本地 mnemopi |

## 4. 客观结论（含自我修正）

第一版对比有偏袒 V4 的倾向（"完胜/碾压"措辞），核查后修正：

1. **V4 的"克制"部分是设计意图，不是已兑现能力**——§12.18 的 7 种更新方式多数未接通
   自动链路（真实自动只有章节学习审查）。少写不是因为过滤得好，是因为自动链路没接线。
2. **Hindsight 的"不可编辑"被说重了**——OMP 有 mnemopi 本地后端支持完整 memory_edit；
   Hindsight 服务端不可编辑是设计选择（保护一致性）。
3. **Hindsight 有 V4 没有的能力**：mental models 的 delta 自动刷新（服务端 consolidation 后
   自动更新总结，agent 零成本）、per-project-tagged 精细作用域。
4. **V4 确实强的点**：用户主权/可解释性（可读可改可锁+变更通知）、模型无关、策略决策输出
   （心智=规划器而非注入常量）。

## 5. 决策：值得学 vs 不值得学（按克制原则过滤）

**值得做（3 条，全部是"补 V4 自己蓝图里未接线的部分"，非抄 Hindsight）：**
1. 会话归档/结束时自动入队 refine（DESIGN 方式 #2 的落地）→ **S132 完成**
2. 确定性操作信号入口（章节保存/定点编辑 → modified，不猜语义）→ **S132b 完成**
3. 跨会话对账落地——**定案为 agent 工具 mind_reconcile 而非周期任务**（只读分析结果需
   人工消费，周期跑白烧 token；V4 无调度机制，定时器违背克制）→ **S132c 完成**

**刻意不做（4 条）：**
| Hindsight 特性 | 不学的理由 |
|---|---|
| 向量检索 | V4 已论证（模型无关/人机双读/规模小）；心智是小规模结构化数据 |
| transcript 全量 retain | 与克制写入哲学冲突；写作偏好噪声代价远高于编码（编码有 git 兜底） |
| 全自动零配置生命周期 | 用户主权+人工闸门是低频高价值场景的合理取舍，不是缺陷 |
| per-project-tagged 三态 | 一人写几本书的两层结构够用，标签系统是过度设计 |

## 6. 长会话标准重定（主人关切：主流模型已 1M 上下文）

- **旧标准错在**：">100K token 启用多步聚焦"与模型窗口强耦合（V4 DeepSeek 缺省 64K 窗口，
  1M 窗口模型上 100K 又太轻）；且它是给"transcript 全量通读"设计的，V4 瓶颈不在这。
- **新标准（S132 定案）**：问题不是"会话多长"，而是"未提炼信号积压多少"——signals 表加
  processed 标记（增量游标），refine 只提炼未处理信号（单批 ≤20，积压分批 + merge_add 归并）。
  阈值语义从 token 数改为积压量，与模型窗口彻底解耦，64K 还是 1M 都成立。YAGNI 不引入
  重型多步聚焦（索引→深读→归并）。

## 8. 残留问题与后续建议（诚实清单）

**已确认未修复（不阻塞主链路，但真实使用会碰到）：**

1. **对话内否定语句仍无自动信号入口**（最实质的缺口）：
   - S62 删了正则机械捕获（对），但入口也删了——用户说"不要用感叹号"这类对话内表述，
     目前只能靠：a) agent 自觉调 mind_register（依赖 LLM 自觉，S74c 实测"正文转述不可靠"）；
     b) 手动 /api/signals。
   - S132b 补的是**操作信号**（保存/编辑），不是**对话信号**。
   - 建议：在对话流程中对"用户明确否定/撤回"动作记录原文进 signals（不猜语义，判定交
     提炼 LLM），与 S132b 同一哲学。**本轮未做（改动在聊天主链路，影响面大，需单独评估）。**
2. **merge_add 碎片治理**：3 个双字词重叠阈值拦不住 2 词重叠的近似条目（实测"叙事克制，
   少用感叹号"[habit] 与"避免使用过多感叹号"[style] 并存）。DESIGN §12.33 已记录历史同类
   问题（"叙事克制"×5 + 一条合并 5 条内容的碎片），**历史脏数据仍在库里**。
   建议：单独数据治理（按需），不阻塞。
3. **多书信号硬编码 main**：refine_from_signals 与 SignalCollector 绑定 book_id="main"，
   非 main 书的信号不提炼。本次保持一致（DESIGN 有 book_id 分层规划），多书场景再扩展。
4. **对账 prompt 不含信号 context**：build_reconcile_prompt 只送 kind+content，LLM 看不到
   信号场景（稿纸/对话），对账精度略降。小问题，改 prompt 需回归 /api/mind/reconcile。

**真实可用性评估**：链路已通（三次真实 DeepSeek 端到端验证：自动提炼/操作信号/对账工具），
但**"真实可用"的唯一检验是真实使用**——此前智能体真实使用暴露的问题（S62 正则误判、
S74c 转述不可靠等）都是上线后才发现的。建议：主人真实用几轮写作+对话，观察信号是否合理
入库、提炼是否误判、对账是否触发，pi 侧盯 data/logs/anyspark.log 与 signals/manual 表，
发现问题即修——这比宣称"已修复"诚实。
