## 一、项目定位与愿景

### 这是什么

AnySpark V4 是一个 **AI 小说创作引擎**——最终目的：AI 写小说。但它不是"AI 辅助写作工具"（如 NovelAI / Sudowrite），而是试图成为一个 **写作领域特化版 pi**（pi = 通用编码 agent 框架）。这个定位决定了它的全部设计取舍。

### 愿景的核心

**"写作即对话"**——用户说话，智能体直接写；智能体的第一能力不是守规矩，而是 **懂你**。北极星体验是"摩擦前置且递减"：把传统写作软件的"写完才发现不对→返工"变成"事前对齐→零返工"。

### 评价：愿景清晰且有深度

这不是一个"套壳 GPT 加个编辑器"的项目。DESIGN.md 1713 行设计规格背后是一套完整的写作哲学：

- "大模型是概率探索器，优秀作品在低概率高价值区"——承认 LLM 的根本局限
- "种子=创作动力≠结构关键点"——理解创作心理
- "航向系统而非护栏"——明白约束与创造的关系

**这些认知在同类产品中极其罕见。** 大多数 AI 写作工具的设计哲学是"加功能加模板"，AnySpark 的设计哲学是"理解创作的本质矛盾并系统化解决"。

## 二、设计哲学的成熟度

### 最突出的三点

**1. "摩擦前置且递减"是真正的产品洞察**

传统写作软件的摩擦曲线是 U 型（开始轻松→中间发现问题→最后返工最痛）。AnySpark 试图把摩擦前置到种子阶段（便宜的对齐），后续递减。这不是"体验优化"，是对创作流程的重新设计。

**2. "对齐优于记忆"是正确的技术判断**

DESIGN.md 明确论证：记忆路线有"存储-检索完备性无法达到"的本质困难；对齐追求"方向正确"而非"完整记录"，信息密度更高（一条偏好陈述指导几百次写作）。这是经过深思熟虑的路线选择，不是偷懒。

**3. "机制硬编码、内容自然语言"的边界划分**

明确区分了三类：过程控制硬编码（循环/工具协议/安全底线）、交互载体结构硬编码（卡片形状）、数据存储结构硬编码（schema）；而把创作内容完全交给模型。这避免了两个陷阱：过度工程（用规则限制模型）和过度放任（靠模型自觉保证安全）。

### 设计哲学的薄弱点

**1. 理论框架过于宏大，验证标准偏软**

T7 验证标准（修改率↓/提问率↓/完成率↑）是合理的代理指标，但：

- 180+ 阶段的开发过程中，**从未系统性地跑过这些指标的纵向追踪**
- benchmark 对比层诚实地承认"短/中程任务裸 LLM 与 AnySpark 质量相当"——价值在长程，但长程验证数据不足
- 1482 章真实数据存在，但多为导入的整书（1282 章哈利波特），自主创作的长程数据（main 33 章）不足以验证"长书一致性"承诺

**2. "写作领域图灵完备"的宣称需要更严格的落地**

第三方哲学审查已经指出：四支柱三真一断，执行完备性有两个断链（reference_lookup 装配缺席、前端按钮指向不存在的端点）。这些是"设计层正确但实现层接线断了"的问题——说明设计规格的完整度超过了实现的落地度。

## 三、功能架构评价

### 架构的成熟度

**分层架构清晰且一致**：`core ← 领域包 ← app`，单向依赖无环，core 不依赖任何包。12 个包各司其职，这是正确的工程选择。47 个 agent 工具 + 166 个 HTTP 端点 + 22 个数据载体，规模已经是一个中型系统。

**十大核心机制**覆盖了写作全链路：

1. 探索-判别双循环（种子→方向→选优）
2. 能动性协议（AI 做多少的五级）
3. 对齐系统（替代记忆系统）
4. 低摩擦交互（操作式表达）
5. 前端空间设计
6. 结构模式模板（三层体系）
7. 多智能体探索
8. 用户自定义规则
9. 检测网（三层协作）
10. 资料消化

### 功能的过度丰富 vs 落地度

**这是项目最大的张力**。186 个开发阶段堆积了大量功能——拆书四步法、工作流引擎、角色推演、评审团、批量改写/审读、叙事树、心智模型 L2/L3、信号提炼……能力清单极其丰富。

但第三方审查揭示了多处"设计宣称与实现脱节"：

- **对齐闭环半通**：5 种信号只有 modified 真实活着，"选候选卡"这个最高频的判别动作从未接线发信号
- **图谱注入过期宣称**：S58 已停止常驻注入，但代码仍宣称"已自动注入"，教 agent 不查证
- **检测网长章覆盖空洞**：>6000 字的章节后半段零覆盖
- **说明书"用户是最终编辑者"未落地**：前端只能看+锁定，不能增删改

**核心矛盾：功能广度 > 功能深度。** 很多功能在"有"和"好用"之间——它们存在（端点/工具/测试），但闭环不完整或接线断了。

### 前端与后端的失衡

**27 个前端 tab** ——这是一个很大的数字。对比之下，主流 AI 写作工具的交互层都很克制（NovelAI 基本就是编辑器+设定卡）。

- **正面**：功能完整、用户有充分控制权
- **负面**：认知负担重——用户需要理解对话/探索/章节/叙事树/工作流/知识库/大纲/伏笔/资料/参考书/技巧/评审团/简介/AI倾向/批量/模板/扩展工具/互动推演/维度/代码/上传/AI文件……这些概念。DESIGN.md 第 1 条原则是"易用——用户上手成本趋近于零"，但 27 个 tab 与此矛盾

这与设计哲学中的"平滑性——从只有灵感的人到有完整规划的作家都能用好"存在张力。当前实现更偏向"给专业用户的全功能控制台"，而非"随使用浮现能力的渐进式工具"。

## 四、技术决策评价

### 正确的决策

**1. SQLite 而非 PostgreSQL**

嵌入式零安装、用户双击即用、数据文件可整体拷贝。对个人创作工具来说是正确的——"升级=替换程序，数据不丢"。

**2. Python + uv workspace monorepo**

12 个包边界清晰，uv 锁文件可靠。Python 生态对 AI/LLM 最友好，uv 解决了依赖管理的痛点。

**3. 不做旧数据迁移（决策 A）**

"绿地独立建设，不背沉没成本"——很多项目死于历史包袱。这是正确的果断决策。

**4. 全部真实实现（决策 B）**

禁止模拟/降级——保证了"功能是真的"而非演示。

**5. 运行时模型注册表（S47）**

多协议（openai/anthropic/gemini/responses）+ 热切换 + 思考强度分级 + 本地 LLM 支持。这让项目不绑死在单一模型上，有长期生命力。

**6. httpx2 迁移等 starlette 原生支持**

不追新、不冒进，等时机成熟再迁移。体现了克制。

### 需要反思的决策

**1. 前端技术栈的复杂度**

React 19 + Vite + Tailwind 4 + TipTap + Zustand + framer-motion + 3d-force-graph + d3 + leaflet + react-leaflet……依赖列表相当重。对于一个"桌面壳+本地后端"的个人创作工具，这套前端栈的维护成本偏高。不过这是事后判断——S75 并入前端时可能没有更好的选择。

**2. C 架构（干净写作调用）的实现时机**

S56 才引入"意图模式"（write_chapter 的 intent+references → 干净调用）。实验实证"0 幻觉 vs 累积 3 幻觉"。这是一个 **关键的正确决策**，但它来得太晚——前 55 个阶段积累的写作调用模式可能已经造成了不必要的调试成本。

**3. 工具收编（S129-S135）的方向正确但执行有偏**

第三方审查指出：reference_lookup 是原子查询，应该留工具层但装配漏了，只在工作流 script 里可用——"该降的降了，不该降的也降了"。这是执行层面的偏差。

## 五、演进健康度

### 极强的迭代纪律

这是项目最令人印象深刻的方面：

- **PROGRESS.md 4762 行**的连续台账——每个阶段有根因分析+修复记录+验证结果
- **180+ 阶段编号**无断号、无重号（有撞号让位机制）
- **门禁分层**（L1/L2/L3）+ 敏感文件强制全量
- **并行协作纪律**（声明区/显式 add/行尾纪律）
- **每次回归修复都有因果分析**（如 S181→S178→S174 的回归链条）

这种纪律水平在个人/小团队项目中极其罕见。它保证了项目在 186 次迭代后仍然可维护、可接手。

### 迭代债务

但 180+ 阶段也暴露了 **回归测试不足** 的问题：

- S178 毁了 S174 的修复
- S181 修了 S178 的回归
- S184 修了 S181 的盲区
- S186 修了前端的显示问题

这种"修 A 坏 B → 修 B 坏 C"的模式说明测试覆盖有盲区，特别是跨功能的集成测试。

### 文档债务

26 个 .md 文件中有些是历史快照（BACKEND-ISSUES 已修复但仍标注"待修复"、FRONTEND-GAPS 已补全）。UML 图过期（画了不存在的端点）。第三方审查明确指出"地图更新纪律（S78 固化）未被严格执行"——这是知识传递的风险。

### 真实使用数据

```
哈利波特:           1282 章（导入整书——拆书测试数据）
第一卷_全173章:      164 章（导入）
main:                33 章（自主创作）
测试之书:              3 章（测试）
```

**自主创作的长程数据不足。** 项目设计承诺"长书一致性"，但 main 只有 33 章，不足以验证。哈利波特 1282 章是拆书/图谱抽取的测试数据，不是创作工作流的真实使用。

**说明书条目只有 14 条，技巧 11 条。** 这意味着对齐系统和技巧提炼系统虽然功能完整，但实际使用深度有限——还没有被真正"用起来"到产生足够数据来验证有效性的程度。

## 六、项目级别的核心风险

### 🔴 风险 1：功能丰富度与使用深度的剪刀差

项目有 47 个工具、27 个前端 tab、166 个端点——功能极其丰富。但真实使用数据（14 条说明书、11 个技巧、33 章自主创作）显示，**大部分功能可能处于"实现了但没被真正用过"的状态**。

如果继续加功能而不深化已有功能的使用，项目会变成一个"什么都有但什么都不深"的陈列馆。

### 🔴 风险 2：设计宣称与实现落地的系统性偏差

第三方哲学审查揭示的不是个别 bug，而是一种 **模式**：设计文档说 A，实现做到 A'（接近但不完整），代码注释宣称 A（过期文案）。这种偏差如果不系统性修复，会侵蚀项目的可信度——用户/后来者无法判断哪些是"真的"哪些是"宣称的"。

### 🟡 风险 3：27 个 tab 的认知负担

当前前端更像"给开发者看的功能展示"而非"给作家用的创作台"。DESIGN.md 的"摩擦前置且递减"理念在前端层面没有充分体现——27 个 tab 本身就是摩擦。

### 🟡 风险 4：单一模型依赖

虽然有多模型注册表，但实际只用 DeepSeek（deepseek-v4-flash）。如果 DeepSeek 变更定价/下线模型，项目会受到直接影响。本地 LLM 文档（vLLM/LM Studio/Ollama）存在，但未见实际使用记录。

### 🟡 风险 5：无 CI/CD

有 `.github/` 目录但无 CI 配置。门禁全靠本地手动跑。对于 186 阶段的项目，这意味着合并质量完全依赖个人纪律——虽然有极强的纪律传统，但这不可持续。

## 九、给项目的三条建议

### 建议 1：冻结功能扩展，进入"深化收敛"期

不再加新功能，系统性修复第三方审查指出的"宣称与实现脱节"：

- 图谱注入过期文案（schemas.py / tools_domain.py 中的"已自动注入"）
- 对齐信号接线（accept/rejected/negative 信号的前端产生路径）
- 检测网截断（reviewers.py 的 6000 字覆盖空洞）
- 说明书可编辑性（前端增删改能力）
- reference_lookup 装配（agent_factory 补传 library）
- 前端"校验一致性"按钮（接入真实能力或删除）

让已有功能真正闭环，而非继续堆积新功能。

### 建议 2：用真实长程创作验证核心承诺

用 main 项目自主创作 50-100 章，追踪 T7 指标（修改率/提问率/完成率），用数据而非设计文档证明：

- "长书一致性"——跨章名字漂移/设定违规/伏笔遗忘是否真的为零
- "对齐累积有效"——提问频率是否真的递减、修改率是否真的下降
- "摩擦前置且递减"——用户是否真的越来越少需要手动修正

当前 benchmark 对比层已诚实地证明"短程任务 AnySpark 与裸 LLM 质量相当"。真正的差异化在长程——需要用长程数据来证明。

### 建议 3：前端做减法

27 个 tab 收敛到核心创作流（对话/章节/探索/伏笔/知识库），其余降权为"按需呼出"或"高级设置"，真正落地"摩擦前置且递减"的北极星体验。

当前 27 tab 的每一个都有 API 支撑和前端实现——它们是真实的。但真实不等于应该平等展示。用户心智模型是"我在写小说"，不是"我在管理 27 个子系统"。
