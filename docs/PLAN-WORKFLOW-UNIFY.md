# 规划：工作流统一化——固定流程工具收编为预置工作流模板

> 状态：**第 1+2 批已实施**（S129 拆书打样 + S133 批量改写/审读模板；主人 2026-08-13 拍板后实施）
> 关联：S40 批量改写/审读 · S59 工作流扩展包 · S102 批量提议 · S114 拆书三层
> 性质：架构优化候选。本文件是**思路与决策依据**，不是实现规格；实施前需主人逐条拍板。

## 一、背景与动机

当前 agent 工具约 **30 个 spec**（分布 10 个文件），其中一部分本质是**硬编码的多步固定流程**，
而非原子动作：

| 工具 | 本质（多步流程） | 无 agent 决策 |
|---|---|---|
| skill_refine（拆书） | 采样/选章 → 分批拆解 → 归并 → 骨架扫描 → 定点精读 | ✅ 步骤确定 |
| 批量改写 / 批量审读 | 逐章循环：读 → LLM → 保存 / 审读 | ✅ 步骤确定 |
| 图谱抽取 / 信号收集 / 会话摘要 | 固定处理管道 | ✅ 步骤确定 |

问题：
1. **工具是贵资产**——每个工具要 spec + implementer + 注册 + 测试 + 文档 + BACKEND-MAP 维护；
   把固定流程硬编码成工具 = 用命令式工具承载声明式流程，结构错位
2. **不可组合**——"改写→审读→修复"这类复合流程，孤立工具表达不了
3. **重复基建**——批量队列/进度/失败处理与 workflow 引擎（断点/失败策略/人工确认）职责重叠

## 二、核心判断：工具的合理边界 = 原子动作

> **多步固定工作 = 声明式工作流（预置模板），不该是命令式工具。**
> **真正留工具的只有两类：agent 决策的原子动作 + 一个工作流执行器。**

按此框架，现有 ~30 工具可分类：

- **固定流程类（迁移目标）**：拆书提炼、批量改写、批量审读、图谱抽取、信号收集、会话摘要
  —— 预计收编 6-8 个
- **原子动作类（保留）**：write_chapter / patch_chapter / read_chapter / skill_lookup /
  explore / search_chapters / read_material / run_code / 网页搜索 / fetch 等
  —— agent 在对话中**动态决策调用**，拆不开、不该流程化
- **执行器（新增/复用）**：运行工作流入口（按模板名实例化 + 跑）

**预期收益**：工具量 30 → 约 20；结构统一（单一机制）；流程可组合/断点/失败策略/复用；
新增复合能力（改写→审读→条件修复）不需新工具。

**实时更新注册（工具 vs 模板的本质差异，2026-08-13 主人指出）**：
- 工具注册 = **编译/装配期**：新增或改流程要写 implementer、改代码、重启生效
- 模板注册 = **运行时**：模板是数据（存 WorkflowStore），AI 生成（workflow_generate）
  / 用户编辑即时生效，**无需重启**
- 含义：新流程上线不需要发版——对话里让 AI 生成模板 → 人工确认 → 马上能用；
  改模板（节点/指令）也只改数据不碰代码。这正是"内容数据化"的收益：
  机制代码固定，内容可热更新。

## 三、目标架构

```
对话/前端按钮
   → agent 调「运行工作流」执行器（唯一新工具，或复用 workflow 现有入口）
   → 实例化预置模板（批量改写 / 拆书 / 全书审读 / …）
   → workflow 引擎跑（loop + agent 节点 + 可选 approval 闸门 + 失败策略 + 断点恢复）
   → 结果回给对话 / 落库（upsert 带版本历史等，由 script 节点承载）
```

预置模板 = 项目自带的 workflow 定义（存 workflow 模板库，可被 AI 生成器扩展）。

## 四、规模化用例：小说加料（工作流化的真正价值，2026-08-13 主人提出）

**需求**：小说加料——在原著合适位置插入/扩写色情内容。参考系统流程：
书籍拆封 → 内容总结 → 识别待处理位置 → AI 改写 → 合并输出。
单次处理几百万字（原书 400 万字 → 加料版 1000 万字，1281 章级）。

**能力映射（全环节已有底层能力）**：

| 环节 | 现有能力 | 状态 |
|---|---|---|
| 拆封/导入 | 书库导入（txt/md/docx/pdf + 规则拆章，P3）| ✅ 367 万字实测 |
| 内容总结/全书理解 | 骨架扫描（S114 卷+章标题轨迹 → 结构笔记）| ✅ |
| 识别待处理位置 | 机关章定位模式（关键词定位+分批识别）——加料点=章内对话/独处/过渡/张力处 | ⚠️ 换指令即可 |
| AI 改写 | 批量改写（S40 逐章保持剧情一致）+ read/patch/upsert | ⚠️ 加料=定点插入非整章改写 |
| 合并输出 | 章节存储 + EPUB 导出 | ✅ |

**规模真相（主人判断准确：主循环做不了几千章）**：
- 主循环 = 对话式任务（三五章）：上下文有界、轮次有限、状态在会话内
- 数千章 = 后台引擎遍历：批量改写（S40）早已示范脱离主循环（tasks.py 后台队列逐章
  独立 LLM 调用，主循环只做发起/批准/查进度）
- **几千章真正的坎**：当前后台队列内存级进度（进程挂=丢）/无断点恢复/无失败持久化——
  workflow 引擎正好补齐（store 持久化 + 断点恢复 + FailPolicy + approval 抽查）

**加料 = 遍历集合工作流的天然用例**（预置模板）：
```
骨架扫描（理解全书）
→ loop 遍历章节集合（约 300 批，5-8 小时后台跑）：
    识别插入点（agent 节点：章内候选位置+上下文）
    → 生成插入段（agent 节点）→ 拼接保存（script 节点，upsert 带版本快照）
→ 可选 approval（每批人工抽查质量）→ 导出加料版
```
workflow 四特性全用上：遍历集合 / 断点恢复（中途进程抖动不重来）/ 失败策略（单章
失败跳过或重试）/ 人工抽查（质量闸门）。**加料、润色、翻译、扩写是同一形态**——
一个"遍历章节 + 自定义指令"的通用模板全包。

**硬门槛（非工程）**：NSFW 内容生成可能被模型服务内容审核拦截（S113 实测
`data_inspection_failed`）。实施前必须先小成本实测（3-5 章）当前模型通道能否产出加料
内容——被拦截则需先解决模型通道（换模型/provider），这是前置条件。

**意义**：工作流化不止"减工具"，更**解锁固定管道型规模化需求**——主循环负责入口与
把关（选书/定指令/批准/抽查），后台流程负责遍历，规模天然可扩展。

## 五、支撑能力缺口：定时调度 + 完成通知（2026-08-13 查证，规模化场景的配套）

**现状（全仓查证）**：
- **定时调度层不存在**：server/workflow 无 cron/scheduler/timer 机制，所有任务只能
  手动/对话触发（唯一 interval 是 workflow 重试间隔，非定时任务）
- **workflow 无唤醒主循环的节点**：NodeKind 固定 agent/script/approval/gate/loop，
  无 notify 类节点；跑完仅状态→done 存 store，**不主动通知**（主循环不会被唤醒，
  只能 workflow_status 轮询）；后台任务（batch）同理，无事件推送层
- 前端 SSE 通道存在，但后端没有"任务完成 → 推送"的机制

**为什么需要**（加料等长流程场景）：
- 5-8 小时后台流程跑完，系统不主动告知——需完成通知（"跑完了，回主循环汇报/接续"）
- 定时场景（"每晚自动跑一批"）需调度层

**两条补法（方向，不实现）**：
1. **定时调度层**：轻量 scheduler（后台线程 + cron 式规则），触发点 = "启动某 workflow
   模板"（复用 workflow_run 语义）——"每晚自动跑加料批"表达为一条 cron 规则
2. **完成通知**：workflow 引擎加 on_complete 回调（完成时注入结果到指定会话 / 触发
   SSE 推送）——前端 useSSE 通道现成，后端补事件即可

**边界（防错位）**：唤醒的是"通知主循环/用户"（汇报结果、接续下一步），**不是**让主循环
去处理几千章——规模仍由后台流程承担，主循环只做入口与把关。

## 六、衔接：workflow 节点导入 skill（与 PLAN-SKILL-UNIFY 交汇，2026-08-13 主人提出）

**现状**：WorkflowNode.params 是自由 dict（instruction/delegate/output_key 为约定俗成，
非硬 schema）——节点加 skills 参数**零引擎改动**。

**三种形态（按注入深度）**：
1. **直接注入**：agent 节点 params 加 `skills: ["斗破苍穹"]`，执行时把 skill content 拼进
   节点 prompt（"按这本书文风写这段"）
2. **子 agent 按需查**：delegate 子 agent 的 tools 白名单加 skill_lookup（已有工具），
   指令说"查《猎手准则》文笔再写"——遵循 S60 注入瘦身（索引常驻 + 按需细看）
3. **模板参数化**：workflow 模板声明 `{style_skill}` 参数，运行时绑定具体 skill——
   **同一模板换 skill 换风格**（加料模板 + 斗破文风 = 斗破味加料，不复制模板）

**价值（流程与知识解耦）**：
- skill 成为 workflow 节点的"知识底座"——流程决定做什么，skill 决定怎么做
- 呼应 PLAN-SKILL-UNIFY 统一容器：type 决定注入时机（writing→生成节点、plot→探索
  节点）、书名包 = 整包风格参数（一次点名拿到全包）
- **单向依赖**：workflow → skill（流程引用知识），不反向——无循环依赖

**边界（保持分工）**：节点导入 skill 是"执行时带上知识"，不是把 skill 变成流程——
workflow 仍是执行容器，skill 仍是知识容器（PLAN-SKILL-UNIFY 的分层不变）。

## 七、边界条件（必须守住，防止"为了统一而统一"）

1. **agent 决策点必须留工具**
   工作流表达"预定步骤"，表达不了"此刻该不该探索/怎么写"——write_chapter/explore 等
   决策型动作流程化是错位（YAGNI 反向：过度统一）。

2. **人工闸门按操作轻重保留（不是全都不带检测）**
   - 轻操作（提炼/摘要/抽取）：非全程，直接出结果 ✅（对应主人说的"不带检测节点只出结果"）
   - 重操作（批量改写覆盖原稿）：必须保留 approval 节点（S32 实证：错误进主链路的代价）
   - workflow 的 approval 节点天然承载此职责——"非全程"指不需人盯每一步，不是重操作免检

3. **workflow 能力缺口先补**
   批量类操作是"**遍历集合**"（每章一次），workflow 的 loop 是"迭代直到条件"（同一节点
   重复跑）——语义不同。两条路：
   - 给 workflow 补集合遍历原语（loop 支持"对集合逐项"），或
   - script 节点做调度循环（runner 里"取第 i 章 → 喂 agent 节点 → i+1"）
   迁移前必须验证一种能干净表达。

4. **模板本身也是成本**
   每个模板要定义/校验/测试，与写工具成本相当——**只有"可复用/可组合/需断点"的流程才值得
   模板化**；一次性动作仍走原子工具。

## 八、迁移路线（分批，每批独立验证 + 可回退）

```
第 1 批（打样）：拆书（skill_refine）→ workflow 模板
   验证标准：模板跑出的结果与现工具一致（同输入对拍），含骨架/精读/案例校验全链路
   产出：workflow 表达"多步 LLM 管道"的可复现样板 + 集合遍历问题的答案
第 2 批：批量改写/审读 → 模板（含 approval 闸门 + 进度回传） ✅ S133
   验证：逐章循环语义 OK（集合遍历 S129 已验证）；前端 BatchPanel 对接或改造
   （工作流模式开关：改写带确认闸门弹窗，审读直跑）
第 3 批：图谱抽取/信号收集/摘要等轻流程 → 非全程模板（直接出结果）
   验证：后台自动跑，结果落库形态与现一致
每批：跑通 → 对拍 → 删对应工具/精简注册 → 全量 gate → 更新 BACKEND-MAP/文档
```

## 九、风险与回退

| 风险 | 缓解 |
|---|---|
| 高频操作便捷性倒退（对话一句话 vs 手动选模板）| 预置模板 + 快捷入口（对话/按钮 = 实例化模板并跑），**归一不降级** |
| 回归（batch 已稳定演进三轮 S40→S102→S109）| 分批迁移 + 每批对拍测试 + 可回退（工具暂留，验证后删） |
| workflow 表达不了集合遍历 | 第 1 批先验证，跑不通则先补原语，不硬迁 |
| 模板爆炸（每个流程一个模板）| 边界第 4 条：只有可复用/可组合/需断点才模板化 |

## 十、待主人拍板的决策点

> ✅ **已拍板（2026-08-13 主人全部确认）**：W1-B（归一不降级）/ W2（轻=只读/新建、
> 重=覆盖/删除/大批量→强制 approval）/ W3-A（补遍历原语）/ W4（拆书打样先行）/ W5
> （加料作验证用例但先实测审核坎）/ W6（完成通知纳入、定时延后）/ W7（模板参数化先行）

1. **迁移深度**：A 彻底归一（工具全删，只剩执行器+模板）/ B 归一不降级（工具变快捷入口，
   底层走 workflow）/ C 并存（先加模板，工具暂留）
2. **闸门策略**：哪些操作允许"非全程直接出结果"、哪些必须 approval（轻/重分类清单）
3. **集合遍历**：补 workflow 原语 vs script 调度循环（技术路线）
4. **优先级**：拆书打样先做，还是先做高频的批量改写？
5. **加料模板**：是否作为第一个规模化用例（验证遍历集合 + 断点恢复 + 审核前置实测）？
6. **定时/通知**：是否纳入首批能力（配合加料模板——定时调度层 + 完成通知回调）？
7. **节点导入 skill**：三种形态选哪种先行（直接注入 / 子 agent 按需查 / 模板参数化）？
   ——依赖 PLAN-SKILL-UNIFY 统一容器（skill 有 type/包结构才能类型化引用）

## 十一、一句话总结

> 固定多步工作 = 声明式工作流模板，不该是命令式工具；
> 工具只留 agent 决策的原子动作 + 一个执行器；
> "非全程不带检测"适用轻操作，重操作保留 approval 闸门；
> 主循环只做入口与把关，规模化靠后台流程遍历（加料/润色/翻译/扩写同一形态）；
> 分批迁移、每批对拍、可回退——不是一次性大重构。
