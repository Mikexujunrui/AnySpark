# AnySpark 3.2.0 今晚最终版：使用、Skills 与发布

> 3.2.0 同版本桌面更新：Windows 与 macOS 打包版现在使用独立系统 WebView 窗口，
> 不再打开默认浏览器。关闭窗口会同步停止后台服务，重复启动只会唤醒已有窗口。

## 1. 这个 Agent 是怎样做出来的

AnySpark 不是“一个特别长的提示词”，而是五层共同工作：

1. **模型层**：DeepSeek、OpenAI 或其他兼容 API 负责理解、规划、写作和评审。
2. **Agent 循环**：模型先决定要读什么、调用哪个工具，再把工具结果带回下一轮。
3. **工具层**：章节读取/写入、知识图谱、评审、参考书分析、Auto 任务等是真正执行操作的代码。
4. **Skills 层**：把多个工具编排成有名称、有顺序、有护栏的工作方法。
5. **项目记忆层**：书籍正文、知识库、大纲、创作宪法、版本历史和参考书分析结果。

因此，Skill 很重要，但不是数量越多越好。一个好 Skill 应该把容易出错的工作固定成少数步骤，
同时明确“不能做什么”。如果 Skill 只是写了一个名称和说明，却没有真实工具、执行路由和护栏，
它不会自动提高正文质量。

### Skill 都要自己写吗

不需要。3.2.0 已内置 11 个系统 Skill。简单 Skill 只需 YAML，不需要写 Python；只有想增加一种
项目里还不存在的能力，例如调用新的数据库、绘图或专业文件格式时，才需要先写新工具代码。

自定义 Skill 保存在用户数据目录的 `data/skills/`，不会因覆盖安装应用而丢失。YAML 的核心字段是：

```yaml
- name: my_skill
  description: "这个技能解决什么问题"
  instructions: "模型执行时必须遵守的专用指令"
  guardrails:
    - "绝对不能做的事"
  outputs:
    - "完成后必须报告什么"
  steps:
    - tool: read_chapter
      label: "读取证据"
      params: {}
```

对话框里输入 `/技能名 你的补充要求` 即可实际执行，不再只是显示技能列表。

## 2. 本版新增的文学 Skills

- `/literary_continuation`：高保真续写新章。确认已有边界，只生成一份草稿，评审不偷改。
- `/author_style_continuation`：学习参考书的句式、节奏、视角、修辞和用词，不带入其他作品人物。
- `/canon_audit`：只读检查人物、时间线、因果、新增设定和原文证据，不自动修改。
- `/surgical_literary_revision`：先指出具体段落和原因，确认后只做最小 patch，不整章重写。

推荐用法：

```text
/author_style_continuation 续写第17章。第三人称限知，重点保持原作者的短句节奏，
不要新增势力，不要解释人物情绪。
```

Skill 不能消灭模型固有的不确定性，但可以把“读证据、只写新章、写后核对、失败不覆盖”变成程序化流程，
显著减少最致命的设定幻觉和误操作。

## 3. 创作宪法怎样使用

每本书首次进入对话前，必须先保存创作宪法。它是该书长期有效的项目规则，会进入普通对话、
直接正文写作、逐节点写作、剧情链复写和 Auto 工作流。

建议把规则写成可检查的句子：

- 好：`全书固定使用林砚的第三人称限知视角；不得描写他不知道的事实。`
- 好：`第12章以前沈青不知道玉佩来源；不得通过旁白提前揭示。`
- 好：`每章对话占比约30%-45%；禁止用总结性旁白跳过核心冲突。`
- 差：`写得更有文学性。`
- 差：`一定要好看。`

“道德绑架模型”通常不会让执行更稳定，反而会浪费上下文。最有效的是明确优先级、事实源、
禁止项、可量化目标和失败时的动作。本版使用程序保护和系统级注入保证规则持续存在，
不靠模型因为受到责备而听话。

## 4. 正文参数建议

设置 → 生成参数只影响正文、编辑和写作工作流，不改变 Agent 的工具选择参数。

| 参数 | 建议起点 | 作用 |
|---|---:|---|
| Temperature | 0.70 | 越高越发散；续写原作不建议一开始超过 0.9 |
| Top P | 0.95 | 控制候选词范围；通常只小幅调整 |
| 频率惩罚 | 0.15 | 减少相同词句重复；太高会损害专有名词和稳定语气 |
| 存在惩罚 | 0.00 | 鼓励新概念；续写时宜低，避免擅自扩设定 |
| 最大输出 Token | 65536 | 输出上限，不代表模型一定写满 |

高保真续写可先用 `Temperature 0.60-0.78 / Top P 0.90-0.96 / 频率惩罚 0.10-0.25 /
存在惩罚 0-0.10`。如果 API 中转不支持某些惩罚参数，程序会自动用通用参数重试。

## 5. 参考书的正确分工

每本参考书有三个用途：

- **只学文风（默认）**：使用结构、句长、段落、对话密度、韵律、修辞、视角和少量分散样本；
  程序禁止搜索和迁移人物、地点、剧情事实。
- **只作原著设定**：适合同人或直接续写原著，只读取其角色、地点和事实，不要求模仿文风。
- **文风＋设定**：同一原著既作为事实源，也作为作者风格样本。

如果当前书是续写 A 小说，而参考书是作者写的无关 B 小说，应选“只学文风”；如果参考书就是 A
小说原文，应选“文风＋设定”。

## 6. Auto 模式现在怎样保证正文

- 新章工具命中已有章节编号时直接拒绝覆盖。
- 导入章节即使标题不是“第 N 章”，也按原顺序记为已存在。
- 一轮只允许一个全章生成工具，后面的写作/存储/重写调用会取消。
- 流式中断时保存已有部分，要求从断点续写，不从头覆盖。
- 逐节点发现问题只标记，不在后台换一份正文。
- 草稿先过质量门，通过后才提取为长期知识；失败或评审异常会暂停。
- 大纲中的章节全部存在时，Auto 返回空计划，不会为了“继续”重写旧章。
- 安全自主模式不会跳过删除、整章替换、局部改原稿和批量修改的确认。

这意味着 Auto 更适合“按已经准备好的大纲依次追加新章”。旧章精修建议使用
`/surgical_literary_revision`，不要把追加写作和旧章重写混在同一个 Auto 任务里。

## 7. 覆盖安装会不会丢数据

可以覆盖安装，正常情况下不会丢：

- macOS：把新 `AnySpark.app` 拖到 `/Applications`，Finder 询问时选择“替换”。
- Windows：运行新版 Setup，稳定 AppId 会识别原安装并覆盖程序文件。

如果正在使用会打开浏览器的旧 3.2.0，第一次覆盖前请从 macOS 菜单栏 `✦ → 退出火花`，
或关闭 Windows 旧版控制台。独立窗口版安装后会显示在 Dock/任务栏，关闭窗口或 `⌘Q`
会一并停止本地后端，后续覆盖安装不再需要寻找隐藏进程。

用户数据不在程序目录：

- macOS：`~/Library/Application Support/AnySpark`
- Windows：`%APPDATA%\AnySpark`

打包版第一次检测到版本变化，会先把 `data/` 备份为：

```text
backups/pre-upgrade_旧版本_to_新版本_日期时间.zip
```

Windows 卸载器也不会删除 `%APPDATA%\AnySpark`。仍建议在跨电脑或大版本更新前，从书架导出 `.spark`
归档；`.spark` 会包含项目正文、知识和创作宪法。

## 8. 为什么 EXE 要在 Windows 验证

EXE 不是“上传 GitHub 后才会变正确”。本机验证的意义是实际启动它，检查 Windows 的路径、
权限、防火墙、浏览器打开、杀毒软件和安装覆盖行为。macOS 无法可靠地验证这些 Windows 行为。

GitHub Actions 相当于一台临时的真实 Windows 构建电脑。3.2.0 支持从网页手动运行 Release 工作流，
无需自己配置 Windows 开发环境；生成后可直接下载 EXE 安装器和便携 ZIP。macOS 任务同时生成
DMG 和 ZIP。

当前安装包没有商业开发者证书：

- macOS 是 ad-hoc 签名，第一次可能需要在“系统设置 → 隐私与安全性”中允许打开。
- Windows 可能出现 SmartScreen“未知发布者”，需要选择“更多信息 → 仍要运行”。

若要让普通用户不看到警告，需要另外购买 Apple Developer 证书并公证，以及 Windows
代码签名证书；这与程序是否能运行是两件事。

## 9. 从零开始上传 GitHub

原项目不属于你，所以不能直接写入作者仓库。你可以发布自己的 Fork，再向作者提交 Pull Request。

### 只发布自己的版本（最省事）

1. 注册 GitHub 账号、验证邮箱，安装 GitHub Desktop 并登录。
2. 在 macOS“终端”中复制执行：

   ```bash
   cd "/Users/ka1ser/Documents/火花mac版/AnySpark-main"
   git init
   git add .
   git commit -m "AnySpark 3.2.0 literary safety release"
   git branch -M main
   ```

3. 在 GitHub Desktop 选择 **File → Add Local Repository**，添加：

   ```text
   /Users/ka1ser/Documents/火花mac版/AnySpark-main
   ```

4. 点击 **Publish repository**。公开发布就取消勾选 “Keep this code private”，然后确认发布。
5. 打开自己仓库的 **Actions → Release → Run workflow → Run workflow**。
6. 等 Windows 和 macOS 两项变绿，点进本次运行，在页面底部 **Artifacts** 下载：
   - Windows x64 Setup EXE 与 portable ZIP
   - macOS DMG 与 ZIP
7. 需要正式版本页时，进入 **Releases → Draft a new release**，创建标签 `v3.2.0`，
   填写 `CHANGELOG.md` 的 3.2.0 内容并发布。标签也会自动触发 Release 工作流，把产物挂到版本页。

### 想把修改贡献回原项目

不要把上面 `git init` 得到的新历史强行推送到 Fork；它与原项目历史不同，通常会被 GitHub 拒绝。
正确做法是：

1. 打开原项目 <https://github.com/Mikexujunrui/AnySpark>，点击右上角 **Fork**。
2. 在 GitHub Desktop 选择 **File → Clone repository**，克隆你刚创建的 Fork，例如保存到：

   ```text
   /Users/ka1ser/Documents/AnySpark-fork
   ```

3. 在终端复制本版源代码到这个带有原项目历史的 Fork。此命令不会复制小说数据、构建缓存和安装包，
   也不会覆盖目标目录的 `.git` 历史：

   ```bash
   rsync -av \
     --exclude='.git' --exclude='data' --exclude='dist' --exclude='build' \
     --exclude='.venv*' --exclude='frontend/node_modules' \
     "/Users/ka1ser/Documents/火花mac版/AnySpark-main/" \
     "/Users/ka1ser/Documents/AnySpark-fork/"
   ```

4. 回到 GitHub Desktop 检查 Changes，填写摘要并点击 **Commit to main → Push origin**。
5. 在自己的 Fork 页面点击 **Contribute → Open pull request**。

如果你已经先按“发布自己的版本”做过，也不影响；贡献原项目时仍使用这个“Fork → Clone → 复制源码”
流程即可。

GitHub Actions 构建不要求把 API Key 上传到仓库。不要提交自己的 `data/`、`.env`、API Key 或小说原稿；
项目现有 `.gitignore` 已排除常见用户数据，但首次提交前仍应在 GitHub Desktop 的 Changes 列表检查一次。

## 10. 同样的方法能否用于其他领域

可以。把“小说工具”换成目标领域工具即可：

```text
用户目标
  → Agent 规划与工具选择
  → 领域 Skills（固定工作方法）
  → 领域工具（搜索、数据库、文件、审批、生成）
  → 证据与长期状态
  → 结果校验和人工确认
```

例如：

- 法务合同 Agent：条款读取、风险规则、版本 diff、审批；高风险输出必须人工确认。
- 研究 Agent：论文检索、证据卡片、引用校验、实验记录；事实必须带来源。
- 游戏剧情 Agent：角色状态机、任务图、对白生成、一致性测试。
- 营销 Agent：品牌宪法、素材库、渠道模板、审校和发布审批。

真正可复用的不是“小说提示词”，而是这套架构：把模型限制在可观察的工具中，把事实放在持久化数据里，
把常见工作写成 Skill，把危险动作交给程序确认，把质量问题留给证据化评审。
